# Issue Solver

Implement a task described by a tracked issue: read the repo, make the code
changes, run tests, commit, reconcile with the base branch, and open a pull
request. This skill is self-contained and driven entirely by inputs supplied
by the launcher -- no harness-injected clients are required.

---

## Procedure

### 1. Orient yourself

You are an autonomous software engineer working in an isolated environment on a
cloned git repository. Your goal is to implement the changes described in the
issue, then commit, push, and open a pull request.

If `{{ORIENTATION_COMPONENT}}` is non-empty, it is a starting map of what the
launcher already knows about this dispatch — the project directory, working
branch, base branch, base commit, any file paths the issue named, and the
validation command. Read it first as a head start, but treat it as pointers to
confirm, **not** a substitute for reading the files you will change:

{{ORIENTATION_COMPONENT}}

Before writing any code:

1. Read `AGENTS.md` and/or `CLAUDE.md` at the repo root and in your working
   directory. These files are the canonical source of truth for how agents
   should operate in this codebase -- build tooling, test commands, code style,
   invariants, and architectural principles. Follow them exactly.
2. Read enough of the codebase to understand the relevant code paths before
   changing anything.

---

### 2. Understand the task

**Task: `{{ISSUE_IDENTIFIER}}` -- `{{ISSUE_TITLE}}`**

```text
{{ISSUE_DESCRIPTION}}
```

If the description is empty, rely on the identifier and title alone. Explore the
codebase to fill in what you need.

If `{{HUMAN_ISSUE_COMMENT_COUNT}}` is greater than zero, the issue has that many
human-authored comments and the description above is **not** the whole task:
teammates often clarify, correct, or extend an issue in the comments. List and
read them before implementing, and fold anything that bears on the work into
your plan. If a tracker CLI is available (e.g. `kikimora-linear comment list
--issue {{ISSUE_IDENTIFIER}}`), use it to read the comment bodies.

---

### 2a. Turn budget and infrastructure blockers

If the launcher supplies a turn budget, treat it as a frame for self-correcting:
if you've spent a significant portion of your budget on a single blocker without
progress, it's time to move on.

If you hit an infrastructure or credential error you cannot resolve — missing
API keys, unreachable services, auth failures, endpoints returning 404 due to
disabled feature flags — and that blocker is **not** on the critical path for
the issue's acceptance criteria, note it as a known limitation in the PR
description and continue with the parts of the task you can complete. Do not
spend more than 3-5 attempts working around a single such blocker; if a
workaround isn't working after a few tries, it won't work on the next try
either. If the blocker *is* the core acceptance path, communicate back to the
launcher and stop rather than opening a partial PR.

---

### 3. Implement the changes

#### Design posture

Before writing code, answer three questions, one sentence each, and put the
answers in the PR description under a **Design** heading:

1. **What is the smallest change that solves this correctly?** Prefer deleting
   or reusing over adding. If the simplest correct behaviour makes an existing
   check or mechanism unnecessary, remove it and say so.
2. **Which existing sibling does this copy?** Before adding any helper, config
   field, env var, secret, endpoint, or auth check, find how the closest
   existing feature does it and do the same. If you must diverge, name the
   sibling you rejected and why. A new secret, injected env var, or authed
   endpoint also needs a one-line row in
   `docs/operations/infrastructure-surfaces.md` naming the canonical channel you
   rejected (KIK041).
3. **Does the ticket match reality?** If the ticket as written conflicts with
   the repo's documented principles, an existing mechanism, or technical
   reality (wrong layer, impossible dependency, feature already exists), do not
   silently build it: flag the conflict — pause for clarification if that path
   is available in your environment, otherwise implement the conforming variant
   and open the PR description with what you changed and why.

Name things for the general concept, sized for the next three members of the
set — never for the customer, ticket, or example that triggered them.

#### Working alongside other pull requests

<!-- launch-parity: rule=pr-authoring.external-pr-ownership -->
Treat any other PR and its branch as externally owned. You may inspect it. Post
a comment only when a user specifically requests interaction with that PR, and
limit the interaction to that comment. Do not modify its code, metadata,
reviews, or lifecycle directly; its authors and owners decide whether and how
to act on the comment.

When commenting on any other PR, identify the comment with the current ticket,
when there is one, and the scope. If this work has no ticket, state the scope
and that no ticket is associated with it; do not invent one. This attribution is
not required on the PR this agent is working on.
For example:
`Context: This implementation agent is working on
{{ISSUE_IDENTIFIER}} — {{ISSUE_TITLE}}.` Link the tracker issue when its URL is
available: {{ISSUE_URL}}.

#### Write for humans, not like an LLM

Everything a human reads, including the PR title and description, comments, and review
replies — is human-facing. Write it like a capable colleague would, not like a
language model. Use simple technical English (for example, ASD-STE100). Length and complexity are costs:

- Lead with the answer, result, or conclusion when you have one. For
  clarification requests, lead with the missing fact or question.
- Use short, direct sentences and concrete verbs.
- Prefer succinct bullets over long prose when they improve scanning.
- Cut filler and self-narration: no "Certainly" and no task restatement.
- Avoid inflated adjectives such as "robust", vague hedging, and rule-of-three
  padding.
- Keep needed facts, requirements, symbols, files, and errors. Do not invent
  details. Do not dress a small change up in systems jargon.
- State unknowns and open questions directly instead of guessing.

Be concise, but keep information needed to understand or complete the work.

Then implement:

1. Make the code changes described in the task.
2. Follow the conventions, style, and architectural rules from `AGENTS.md` /
   `CLAUDE.md`.
3. Do not introduce changes outside the scope of the task.
4. When `{{ASSIGNEE_EMAIL}}` is non-empty, retain the bot as the primary
   author and add this separate trailer paragraph to **every** commit you
   create: initial work, checkpoints, test-fix follow-ups, and re-dispatch
   work:

   ```text
   Co-authored-by: {{ASSIGNEE_EMAIL}} <{{ASSIGNEE_EMAIL}}>
   ```

   Pass `{{ASSIGNEE_COAUTHOR_TRAILER}}` as a second `-m` argument to `git commit`. When
   `{{ASSIGNEE_EMAIL}}` is empty, create ordinary commits with no co-author
   trailer.

#### Where documentation belongs

If your change needs documentation, put the content in the right place rather
than appending it to `CLAUDE.md`. A `CLAUDE.md` is an **index** -- a
navigational map pointing at docs -- not a content destination, and many repos
gate any change to `**/CLAUDE.md` behind mandatory human review, which blocks
auto-merge on otherwise routine PRs.

- **New feature, operational detail, or architectural change** -> create or
  update a file under `docs/` (e.g. `docs/operations/my-feature.md`) and update
  the relevant `docs/` index or `ARCHITECTURE.md` to link it.
- **New module or package** -> update `ARCHITECTURE.md`; add at most a **one
  pointer line** to the code map in `CLAUDE.md`. Do not write the feature
  description into `CLAUDE.md` itself.
- **Change to an existing area already indexed in `CLAUDE.md`** -> update the
  destination doc only; do not touch `CLAUDE.md` at all.

Defer to the repo's own `AGENTS.md` / `CLAUDE.md` if it states a different
documentation convention.

#### Name the invariants your change assumes

A change almost always introduces or starts relying on a non-obvious property
that nothing yet enforces -- "callers always pass an absolute path here", "this
list is deduplicated before it reaches that loop", "this field is never blank".
Left implicit, such a property is rediscovered only when a future change breaks
it and a bug surfaces. Before you finish, spend a moment to surface them. This
applies to **both** feature and fix work -- the question is "what does this
change now assume?", never "what bug did I just introduce?".

1. **Name** the non-obvious invariants/assumptions your change introduces or now
   depends on.
2. **Record** each where the repo prescribes (its `AGENTS.md` / `CLAUDE.md` will
   point at the right home -- an invariants/principles doc, a design note,
   a docstring) and **at the altitude** the repo prescribes -- prefer a
   mechanical guard (a static check or test) over prose, and prose over nothing.
3. **Encode the guard now when it is cheap** -- a one-line assertion, a small
   test, a doc line -- so it ships in this same change. When a proper guard is
   expensive (new tooling, fixtures, a separate mechanism), **flag a follow-up**
   the way the repo expects rather than padding this PR.

Defer to the repo's own `AGENTS.md` / `CLAUDE.md` for *which* enforcement
mechanisms exist, their preference order, and how follow-ups are filed.

#### Evidence contract

When you demonstrate that a behaviour change works — whether prompted by the
task ("evidence", "prove it", "show me it works", "show me an example",
"demonstrate") or on your own initiative — the expected evidence is an
**end-to-end run through the surface a real user actually hits**: a UI screengrab
or a CLI recording, exercised through the production entry point and mode. Bias
to this real-surface proof first.

An implementation-level argument — a SQL query, unit-test reasoning, a hand-run
of a single code path, a synthetic replay — is a **fallback**, valid only when
the real user-facing surface genuinely cannot exercise the behaviour. When you
fall back, say so in the PR: state that it is a fallback and why the real surface
could not be used.

**Real-surface evidence** must name the entry point and mode: identify the
surface and config a real user hits and confirm your evidence ran through *that*
path, not an adjacent one. (For search this is hybrid vs text-only ranking;
generally it is whatever entry point and mode production uses for the affected
behaviour.) If the path you exercised is not the one users actually take, the
evidence does not prove the change — redo it through the right path.

**Implementation-level fallbacks** must disclose: that it is a fallback; why
the real surface could not exercise the behaviour; which code path was
exercised; and whether that path matches the production default for the
affected users.

For any evidence, **mark fabricated data as a simulation**: if the
demonstration relies on data or state you created yourself (rows you seeded,
a corpus you loaded), label it explicitly — do not imply it used production or
customer data.

### 4. Run tests and fix failures

For `apps/backend`, run only:

```bash
git fetch origin {{BASE_BRANCH}}:refs/remotes/origin/{{BASE_BRANCH}}
bun run test:affected -- origin/{{BASE_BRANCH}}
```

Do not run `bun run test` or `bun run check` for the backend. Both run the full
backend suite. The full suite runs in sharded PR CI. This backend rule overrides
the general repository instruction to run the full test suite.

Run the test suite as specified in `AGENTS.md` / `CLAUDE.md` (or the project's
own README). Fix any failures your changes introduce. Do not commit with a
broken test suite.

---

### 5. Optional: run `tessl verify`

If a `tessl.json` file exists at the repository root **and** the environment
variable `TESSL_TOKEN` is set to a non-blank value, run:

```bash
cd "$(git rev-parse --show-toplevel)" && tessl verify
```

Fix any reported failures before committing. If either precondition is absent,
skip this step -- do not attempt to install tessl or obtain a token.

---

### 6. Commit your changes

Commit with a clear message that references `{{ISSUE_IDENTIFIER}}`. Scope the
commit subject the **same way as the PR title** below -- same `<type>`, same
`<project>, {{ISSUE_IDENTIFIER}}` scope -- so the commit subject and PR title
never diverge:

```bash
git add <changed files>
git commit -m "<type>(<project>, {{ISSUE_IDENTIFIER}}): <concise description>" \
  -m {{ASSIGNEE_COAUTHOR_TRAILER}} \
  -m "Implements {{ISSUE_IDENTIFIER}}: {{ISSUE_TITLE}}"
```

Use a conventional-commits type that matches the change: `feat`, `fix`,
`refactor`, `docs`, `test`, `chore`, or `perf`. Use the same `<project>` scope
component you will use in the PR title (see **PR title format** below):
`{{PROJECT_NAME}}` if supplied, otherwise the last path segment of the working
directory or the repo name.

<!-- launch-parity: procedure=issue-solver.delivery anchor=reconcile-base -->
### 7. Reconcile with the base branch

Before opening the PR, bring your branch up to date with `{{BASE_BRANCH}}`:

```bash
git fetch origin {{BASE_BRANCH}}
git merge origin/{{BASE_BRANCH}} --no-edit
```

If the merge reports conflicts:

1. Resolve them in the working tree.
2. Stage the resolved files and complete the merge commit:
   ```bash
   git add <resolved files>
   git commit
   ```

Do not re-run the tests yet -- push first (step 8), then verify (step 9).

**Before concluding that earlier work was lost** -- or that a clean working tree
means nothing happened -- verify against the remote (the source of truth):

```bash
git fetch origin && git log --oneline origin/$(git branch --show-current)
```

A sub-agent or workflow step may have committed and pushed from an isolated
worktree, leaving your local tree clean even though the branch already carries
the work.

---

<!-- launch-parity: procedure=issue-solver.delivery anchor=push-branch -->
### 8. Push the branch

Push **now**, before the verification re-run below, so a commit survives even if
you run out of turns mid-verification. This only creates or updates the remote
branch -- no PR yet.

Validate the branch name first -- reject an empty value from a detached
worktree -- then push with `--force-with-lease`, since `{{BRANCH_NAME}}` may
already exist on `origin` from workspace setup or a prior isolated-worktree
commit, which would make a plain `git push -u` fail non-fast-forward:

```bash
BRANCH=$(git branch --show-current)
if [ -z "$BRANCH" ]; then
  echo "No current branch; stop and report the problem instead of pushing."
else
  git fetch origin "$BRANCH" 2>/dev/null
  git push --force-with-lease -u origin "$BRANCH"
fi
```

If that push still fails after fetching -- a real non-fast-forward you can't
safely resolve, or a persistent network/auth error -- do not force over it or
continue silently without the durable remote copy; stop and report the
problem instead.

---

<!-- launch-parity: procedure=issue-solver.delivery anchor=rerun-validation -->
### 9. Re-run the test suite

Now that the work is durable on the remote, re-run the test suite (and the
project's lint/typecheck command, if it has one) against the reconciled tree.
Fix any failures, commit, and push again.

Do **not** open the PR until `git status` is clean and the re-run passes.

---

<!-- launch-parity: procedure=issue-solver.delivery anchor=find-pr -->
### 10. Open (or update) the pull request

First, check whether a PR already exists for this branch:

```bash
gh pr list --head "$(git branch --show-current)" --state open
```

- **If one is listed**, it is the canonical PR -- push your commits to it and do
  not open a second one.
- **If none exists**, write `pr-body.md` with your **Write tool** — never a
  `cat <<'EOF'` heredoc, whose delimiter a body line can collide with
  (`KIK069`) — holding `<concise description of the changes and motivation>`,
  a blank line, `Closes {{ISSUE_IDENTIFIER}}`, `---`, and `{{PR_SIGNATURE}}`.
  Then create the PR from it:

<!-- launch-parity: procedure=issue-solver.delivery anchor=open-pr -->

```bash
gh pr create \
  --base {{BASE_BRANCH}} \
  --title "<type>({{PROJECT_NAME}}, {{ISSUE_IDENTIFIER}}): <descriptive title>" \
  --body-file pr-body.md
```

<!-- launch-parity: rule=issue-solver.pr-title-shape -->
<!-- launch-parity: rule=issue-solver.conventional-commit-types -->
#### PR title format

```text
<type>(<project-name>, {{ISSUE_IDENTIFIER}}): <descriptive title>
```

- `<type>`: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, or `perf` --
  inferred from the nature of the change.
- `<project-name>`: `{{PROJECT_NAME}}` if supplied; otherwise use the last path
  segment of the working directory or the repo name.
- `<descriptive title>`: a concise description of the specific changes made
  (not a repeat of the issue title).

**Example:**
```text
feat(myproject, EXP-667): Add webhook-triggered dispatch for Linear events
```

#### PR body

Include:
- A concise summary of what was changed and why.
- A `Closes {{ISSUE_IDENTIFIER}}` line so the issue is linked and auto-closed on
  merge (omit this line if the tracker integration is not configured or the
  identifier is not a GitHub-resolvable reference).
- An `Assignee: {{ASSIGNEE_EMAIL}}` line when `{{ASSIGNEE_EMAIL}}` is non-empty;
  omit the line entirely when it is blank.
- The `{{PR_SIGNATURE}}` line, exactly as supplied, as the final line of the PR
  body so the PR is identifiable as launcher-managed. When the launcher supplies
  no `{{PR_SIGNATURE}}`, default to:

```text
Generated by the Tessl Dark Factory
```

<!-- launch-parity: rule=issue-solver.ticket-id-autoparse-guard -->
#### Do not reference unrelated ticket IDs

Reference **only `{{ISSUE_IDENTIFIER}}`** (the issue being worked on) in the PR
title and body. Any *other* bare tracker identifier (e.g. `EXP-1234`,
`DSC-5678`) in a PR title or description is auto-parsed by the tracker↔GitHub
integration, which attaches the PR to that ticket and can move a closed ticket
back to an active state. The `<type>(<project>, {{ISSUE_IDENTIFIER}}):` title
format above already carries the issue's own identifier — that is correct and
intended. If you need to refer to another ticket, use its URL or wrap the
identifier in backticks (e.g. `` `EXP-1234` ``) so the integration does not
parse it as a link target.

## When no code change is needed

If you determine -- after reading the codebase -- that no code change or PR is
required (the work is already done, the request rests on a misunderstanding, or
there is genuinely nothing to implement):

- **Communicate back** to whoever triggered the task. Leave a comment on the
  issue, open a draft PR with an explanation, or post to whatever channel the
  launcher expects -- based on what is available in your environment and what the
  trigger implied. Explain what you checked and why no implementation was
  needed.
- **Exit silently** only if the trigger was pure noise and no response was
  expected.

Do not commit empty changes or open a PR for work that did not happen.

## Notes for launchers

- Supply `BRANCH_NAME` pre-created or allow the skill to create it from
  `{{ISSUE_IDENTIFIER}}` lowercased and slugified (e.g. `ae-667`).
- If the repository requires bot identity for git commits, configure
  `user.email` and `user.name` before invoking this skill, or pass them as
  additional inputs.
- `GH_TOKEN` / `GITHUB_TOKEN` must be set in the environment for `gh pr create`
  and `git push` to authenticate.
- The `Closes {{ISSUE_IDENTIFIER}}` line in the PR body is meaningful only if
  the tracker (Linear, Jira, GitHub Issues, etc.) is configured to resolve
  issues from PR descriptions. Omit it or adapt it to the tracker's syntax as
  needed.
